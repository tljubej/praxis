# Praxis vs Rust vs Python — benchmark report

Generated by `benchmarks/report.py` from `benchmarks/results.json`. See [`README.md`](./README.md) for what each benchmark measures and how the three implementations are kept comparable.

## The short version

Across the 8 benchmarks Praxis is **185× slower than Rust** and **4.6× slower than CPython 3.14** (geometric means of the per-benchmark ratios). It is slower than Python on all 8 of them. The hoped-for landing zone was between Rust and Python, closer to Rust; the measured position is on the far side of Python.

There are two separate findings, and it matters that they are separate.

**The speed is the boxing.** It is not the JIT — the JIT is fine, and the floor measurements below establish that to two decimal places. §4.3 makes every language value a `GcRef` and says so normatively: *no language-visible storage location contains an unboxed scalar.* So `acc + i` is an add plus an allocation plus a header write, where Rust emits one instruction and CPython hits a small-int cache. Every ratio in the table below is a restatement of that one sentence — the benchmarks whose inner loop is arithmetic are the furthest from Rust, and the one whose inner loop is a hash probe is the closest.

**The scale is the collector's pacer, and that is a different problem with a different fix.** `collect_threshold` doubles after every paced collection and nothing bounds it, so peak resident set is a function of how long a program has run rather than of how much it is holding: these benchmarks retain **200–500 MiB per second of runtime** on workloads whose live data is a couple of dozen megabytes. That, not time, is what caps this suite — at roughly 30 seconds of Praxis runtime a benchmark exhausts this 16 GiB machine. The sizes below are chosen to peak near 6 GiB, which is why Rust lands in the tens of milliseconds rather than the few seconds that would be conventional; sizing for a one-second Rust run would need Praxis to allocate several hundred gigabytes. The appendix measures what fixing the pacer costs, and the answer is not what it looks like.

## Where the time goes

### Every value is a heap object

§4.3 is explicit that this is normative: *no language-visible storage location contains an unboxed scalar*, and *an arithmetic result becomes a `GcRef` before it can be stored, passed, returned, captured, or inspected*. So `acc = acc + i` is an add, an allocation, a header write and a root update, where Rust emits one instruction. §4.3 also anticipates the way out — *later optimizations [may] intern small integers, use tagged pointers, or eliminate allocations through escape analysis* — and none of it is implemented yet.

The spread across the suite follows directly. `hashwork` is the closest to Rust (44×) because its inner loop is a SipHash of a key and a probe of a `HashMap` — work both languages pay identically, since the Praxis runtime *is* `std::collections::HashMap`. `collatz` is the furthest (388×) because its inner loop is nothing but arithmetic, so it is nothing but boxing.

### The collector's pacer never comes back down

`Heap::collect_inner` doubles `collect_threshold` after every paced collection (`crates/praxis-runtime/src/heap.rs`), and nothing lowers it again — the only assignment back to `INITIAL_COLLECT_THRESHOLD` is in `reset`, which is teardown. Starting at 64 KiB, the *n*-th collection therefore runs after 64 KiB · 2ⁿ of fresh allocation, and the heap high-water mark before it is that same figure. Peak resident set comes out at **about half of everything the program ever allocated**, independent of how much of it was live: `primes` peaks at 6.67 GiB holding nothing at all. A program that allocates at a steady rate — which is every program in this suite, and every Praxis program, because arithmetic allocates — spends its later life not collecting.

The conventional fix is to set the next threshold from the *live* set measured by the collection that just finished (`live × k`, clamped to a floor), rather than from the previous threshold. That was tried — see the appendix — and the result is worth stating carefully, because it is not the one the paragraph above invites: it cuts peak memory by 123× and costs 14% **more** time, not less. The doubling is not an accident that happens to be slow; it is a trade that buys speed with memory, and it buys it at an unbounded price. What is wrong with the rule is not its rate but that nothing bounds it — a program's resident set is a function of how long it has run rather than of how much it is holding, which is what makes ~30 seconds the longest Praxis run this machine can complete.

### What the sequence pipelines are worth

§6.3 claims a non-barrier chain fuses into one loop over the source with no intermediate `Vec`s (ADR-029). `pipeline` comes out at 282× Rust and 6.9× Python — against Python, the worst ratio in the suite. The fusion is real and it does remove the intermediate vectors; what it cannot remove is the per-element allocation inside the loop it fused, and that is what the measurement is dominated by. Rust's iterators and Python's generators are fused too, so the comparison isn't measuring whether Praxis fuses — it is measuring what a fused element costs.

## What would move these numbers

In rough order of how much each is worth, and every one of them is already sanctioned by the design document rather than a change to it:

1. **Stop allocating for scalars.** §4.3 explicitly reserves this: *later optimizations [may] intern small integers, use tagged pointers, or eliminate allocations through escape analysis… [they] must preserve reference and aliasing semantics.* Nothing else in this report is worth as much. `collatz` — the benchmark whose inner loop is pure arithmetic and nothing else — is 388× Rust; `hashwork`, whose inner loop is a hash probe both languages pay identically, is 44×. The difference between those two figures is the boxing.
2. **Bound the collector's threshold.** Measured below, and it is a *scalability* fix rather than a speed one: pacing off the live set costs 14% more time and cuts peak memory by 123×. That trade is worth taking anyway, because today the thing that decides how large a Praxis program can be is how much RAM it has, not how long you are willing to wait — and a puzzle input that runs for a minute is not an exotic case for the language this one is aimed at. A middle setting (`max(live × k, previous × k)` with a hard ceiling) would keep most of the speed and still bound the growth.
3. **Escape analysis on MIR.** The same §4.3 sentence. A loop-local accumulator that never escapes its function needs no heap object at all, and the fused pipelines of §6.3 are exactly the shape where the intermediate values are provably local.

## Appendix — what the pacer is actually buying

To put a number on the section above rather than leave it as a hypothesis, the pacer was changed to set the next threshold from the live bytes the sweep just measured (`live × 2`, floored at 8 MiB) instead of from the previous threshold, and the suite re-run against that build. Every checksum still matched. **The patch was a scratch experiment built into a separate target directory and reverted; it is not in the tree.**

| Benchmark | Praxis as-is | Pacer patched | Time | Peak RSS as-is | Patched | Memory |
|---|---:|---:|---:|---:|---:|---:|
| `primes` | 13.24 s | 15.73 s | 0.84× | 6.67 GiB | 22 MiB | 308× less |
| `mandelbrot` | 13.63 s | 14.59 s | 0.93× | 7.02 GiB | 24 MiB | 294× less |
| `collatz` | 16.26 s | 18.08 s | 0.90× | 6.51 GiB | 22 MiB | 302× less |
| `vm` | 19.90 s | 20.91 s | 0.95× | 5.88 GiB | 25 MiB | 239× less |
| `hashwork` | 13.99 s | 17.19 s | 0.81× | 6.06 GiB | 44 MiB | 141× less |
| `tree` | 15.75 s | 20.40 s | 0.77× | 5.18 GiB | 123 MiB | 43× less |
| `pipeline` | 17.93 s | 21.04 s | 0.85× | 6.10 GiB | 246 MiB | 25× less |
| `bfs` | 27.18 s | 28.59 s | 0.95× | 6.13 GiB | 122 MiB | 51× less |
| **geometric mean** | | | **0.87×** | | | **123× less** |

The time column is below 1.00×, which means the patched build is **slower** — by 14% on the geometric mean. That is the opposite of what the doubling rule looks like it is doing wrong, and it is the useful result: the unbounded threshold is not a bug that happens to cost memory, it is a deliberate-looking trade of memory for collection frequency, and the trade is a good one right up until the memory runs out. Collecting against a live set this small means collecting constantly, and mark-and-sweep costs more than the page faults it avoids. Meanwhile memory falls 123× and — the part that matters — stops being a function of how long the program has run.

So the gap in the main table is not the collector's to give back. It is the boxing, and only item 1 above reaches it.

## Caveats

- **CPython 3.14 is a fast baseline.** This is a PGO+LTO Homebrew build with mimalloc and the 3.11+ specializing interpreter. Against the CPython most people picture — 3.8, no PGO — the same numbers would flatter Praxis noticeably.
- **Rust is the ceiling, not a fair fight.** It is here to scale the axis. A garbage-collected language with a uniform boxed representation is not trying to reach it.
- **Single machine, single run of the suite.** Best-of-5 on an otherwise-idle laptop; no CPU pinning, no frequency locking.
- **The sizes are memory-bound, not time-bound.** The appendix's patched build runs the same workloads in tens to hundreds of megabytes; the shipping one cannot be sized past this without exhausting the machine.
- **`vm` and `bfs` give Python its two idiom advantages.** A Python `list` of tuples and a `bytearray` are closer to the metal than the tagged union and `BitSet` the other two use. That is the point of comparing idiomatic code, but it is worth knowing which way it cuts.
